## Open items

### Before sharing with other parents
1. **Adult check on the parent area.** Today any child can open it, and it shows the family code and the delete-from-cloud button. Options (recommendation first):
   - *Spelled-out number* ("הקלידו את המספר: אלף מאתיים שלושים וארבע"), a new number each time, about 3 seconds for a parent. Reading long Hebrew number words fluently is rare at this age.
   - *Parent-set PIN* (4 digits, set at first run): most secure, needs a "forgot PIN" path (for example a typed confirmation sentence plus a delay).
   - *Gesture* (press three corners in a set order): language-free, but a child who watches once can copy it, so only as a second layer.
   - *Hold plus a parent-level fact:* works for Israeli adults only; not recommended.
   - Avoid multi-step arithmetic: the whole game trains arithmetic.
2. **First-run walkthrough** for new parents (see Welcome screen).
3. **Reset button** (reset one profile's progress, behind the adult check) and the **storage-persistence request** (`navigator.storage.persist()`), which reduces random deletion of local data.
4. **Emoji replaced by images:** 46 of 114 done (rewards, level and celebration icons, parent-area icons); the rest still show as emoji. See `ICONS.md`.

## Packaging and publishing (changed 2026-11-01)
- **Source of truth stays one file**: `math-quest.html` with every picture and font embedded. All editing and all tests (except `splittest`) use it.
- **Published as a split build**: `python3 tools/build_split.py math-quest.html dist` turns it into a small page (about 0.5 MB instead of 8 MB) plus `assets/<hash>.<ext>` files (about 184 pictures and fonts, content-hashed so an unchanged picture keeps its name), `assets.json`, the manifest, the icons and `sw.js`. Pictures now load only when a screen uses them, a republish only needs to send changed files, and the manifest and home-screen icon links stop returning errors.
- **Publishing steps**: run the full suite, build `dist`, publish `dist/math-quest.html` with the files under `dist/assets/` plus `manifest.webmanifest` and the icons as supporting files (root = the dist folder). One publish can carry 255 files; with more, publish in several calls to the same URL (later calls add to the files already there). Limits: 16 MB per file, 256 MB and 511 files per version.
- **Offline**: `sw.js` caches the page, then every file listed in `assets.json` (best effort). The single-file build has no `assets.json` and works as before.
- **Hosting elsewhere** (for example GitHub Pages): upload the whole `dist` folder as it is.
- **Roll back**: the single file can still be published as is (it works the same, only heavier).
- Test: `splittest` builds the split version, serves it and checks that nothing is embedded, every link resolves, every picture, icon and font loads, with no missing files or errors.

## Varied rewards: layered parts (plan agreed 2026-11-01; pilot = cupcake)
**Idea:** every base reward is built from 2 to 4 transparent layers (for the cupcake: base, frosting, topping), each with several variants, so one reward kind has dozens of looks. Decided with Matan:
- The number of parts is flexible per reward kind (2, 3 or 4); we go one reward at a time, starting with the cupcake. Parts are data, not code.
- **Layers, not pre-made pictures.** 5 x 5 x 5 variants would be 125 pictures per reward if pre-rendered, but 15 small ones as layers. Parts are generated on plain white (no transparency available), cut out by script, and lined up by measured contact points (top of the base, bottom of the frosting, bottom of the topping), so the AI does not have to place anything exactly. Some parts get code color shifts (flat pastel parts only) to multiply the variety; a preview sheet is approved before anything ships.
- **Rarity:** some parts are rarer (common / uncommon / rare weights per part); new rewards also prefer combinations the child does not own yet.
- **Rendering:** stacked `<img>` layers (no canvas, so it also works from a local file); a reward with no parts keeps today's single picture, so rollout is per kind and per theme (coverage row for parts in the parent area).
- **Saving:** an item stays a string, `kind:b.f.t` (for example `🧁:2.0.3`), so sync, backup codes and parent screens keep working. Old plain items (for example `🧁`) get a fixed default combination on first load after the update (see "Old rewards migration changed"), saved with a version marker (random per load would change her collection every time).
- **Upgraded rewards stay static for now** (single fixed picture per kind). The same layered-parts rule will be applied to them later.
- **Merged rewards are remembered.** Merging 10 items keeps the 10 combinations inside the upgraded item (for example `kind#2.0.3,1.4.1,...`), so un-merging returns exactly the same ones; looks made from upgraded items keep theirs too. Upgraded items made before this change have no memory and un-merge into fresh random items. Planned later: a view where merged rewards are always visible.
- **Merging still counts by kind** (any 10 cupcakes, whatever their look).
- **Idea, not built:** generated names from the parts ("chocolate cupcake with pink frosting and a cherry"); needs a Hebrew template per kind with correct agreement. For now rewards keep their base name.
- Art kit for the pilot: `reward-parts/cupcake/` (Gemini prompts, style references, rarity plan, cut parts in `parts/`, `parts.json`, scripts in `tools/`, preview sheets).
- **Cupcake pilot result (2026-11-02):** Matan's sheets gave 4 bases, 4 frostings and 9 toppings. Used: 4 bases; 5 frostings (pink, vanilla, chocolate, rainbow, plus the extra lavender dollop, which works as a shorter frosting shape); 7 toppings (cherry, sprinkles, star, heart, strawberry, two unicorn horns; the blue heart is just the pink heart color-shifted, so it is not a separate part). Pink swirl, lavender dollop, star and heart also get 5 color shifts each (0, 70, 140, 210, 280 degrees; the dark outline and near-white highlights keep their color). Total: 4 bases x 13 frostings x 15 toppings = 780 distinct cupcakes from 16 drawn parts. Rarity (weights common 6, uncommon 3, rare 1): rare = gold confetti base, rainbow swirl, both unicorn horns.

## Cupcake's personal space (plan agreed 2026-11-04, not built)

**Idea.** A room that belongs to Cupcake. Every upgraded reward (a merge) earns one **token**. At 10 tokens the room unlocks, and tokens then buy upgrades, new items, colors and patterns, until the room is a space the player designed. First room now; more rooms later. Art reference: `personal-space/` (the room grid template and the Gemini prompts)

**Room size (decided 2026-11-05):** a 10 x 10 floor with a fine tile, so big items span several tiles (bed 4x4, canopy bed 5x5, rug 4x4, desk 2x4, armchair 2x2, plant 1x1) and placement stays flexible without losing detail. Walls are 8 units high (a wall unit is 1 tile wide and half a tile high); a window is 4x4 wall units. **Zoom is essential:** the room opens fitted to the width, pinch/double-tap zooms (up to about 3x) and drag pans, on every screen size..

### Decisions (from Matan's comments)
1. **No un-merge any more.** Rewards are kept in a "memory vault" for good, also after being merged ("spent"). So a token is earned once, at the merge, and there is nothing to revoke. Tokens are a stored counter (`earned`), never derived from the number of upgraded rewards.
2. **Unlock ceremony.** A celebration when the space unlocks: at 10 tokens, or on the first start after this feature ships for a profile that already has 10 or more. Unlocking spends nothing; the balance stays 10. Art: the coin sheet (the treasure chest opening).
3. **One-time true-up.** Existing upgraded rewards count: `earned = upgraded rewards now + 10 per opened look` (looks consumed 10), done once per profile (flag in the save).
4. **Entry points.** The reward vault, and later a place on the game-selection screen (which becomes more map-like, a separate task).
5. **Remove / put away.** Tapping an item offers remove. A removed item stays owned and can be placed again at no cost, on any free cell. An item can only be placed as many times as it was bought (buy two plants to have two). Items placed from the start (bed, window) can also be put away.
6. **Pace and size.** About 300 rewards in a month = about 30 tokens a month. The room should need a couple of hundred tokens to be maxed (about 6 to 7 months at today's pace; the new reward system is meant to keep her playing longer). Prices live in one catalog table, and a check (`max-out cost`, shown in the debug tab and asserted in a test) adds up the whole catalog so tuning is easy.
7. **Colors are bought per item (and per surface).** One token per color per item: the purple wall does not give a purple balcony. A color already bought is free to switch back to; a removed and re-placed item keeps what was bought. Premium colors (gold, silver, rainbow) can cost 2. Surfaces' patterns work the same way (price 2 per pattern per surface, draft).
8. **No selling back** (for now). The buy confirmation says so.
9. **The "looks" are retired** (corrected 2026-11-05: the looks are pictures of the mascot, Cupcake, not of the baked cupcake). The room replaces them. Their 16 pictures join the mascot's standard pictures, the ones picked at random after every answer (7 moods + 16 = 23 in the sweets theme).

### Data model (saved in the profile, `progress.space`)
```js
{ v:1, earned:0, spent:0, unlocked:false, trued:false,
  surfaces:{ wallL:{c:0,p:0,ownC:[0],ownP:[0]}, wallR:{...}, floor:{...} },   // current color/pattern + lists already bought
  items:[ {uid:'i7', id:'plant', lv:0, c:2, ownC:[0,2], at:{x:3,y:4,f:0} | slot:1 | null} ]  // null = put away (still owned)
}
// catalog, in code: ITEMS[id]={place:'floor'|'slots'|'wall'|'ceiling', foot:[w,d], slots:[...], buy:cost, levels:[{cost,art}], tint:bool, colors:[...]}
```
Owned = every entry in `items`; placed = entries with a position; to place another copy of an id the player must buy it again. `cleanProgress` validates it like rewards (unknown ids, levels, colors and positions fall back). It is tiny, so cloud backup and the share code carry it without change. Merge conflicts across devices need care (see the engineering section): `earned` merges by max, purchased lists by union.

### Interaction
**Wording used in this plan.** *Free* always means free placement (an item that can stand on any empty cell, or a surface that can be recolored at will), never price. When something costs nothing the text says *at no cost*. Item kinds by placement: `floor` (any empty floor cell), `slots` (fixed wall spots such as the window), `wall`, `ceiling`.

- **Tap an item or a surface:** a small bubble with Upgrade (price, with a before/after preview of the next level), Color (a row of paintbrushes: bought colors are free and marked, new ones show the price), Move, Put away. Tap and drag are different modes (a Move toggle or long-press), so a tap never moves something by mistake.
- **Placement rules:** `floor` items (placed freely: any empty cell of the floor grid, no fixed spot) snap to the floor grid and must fit inside the room without overlapping another footprint; `slots` items (window) jump between their valid slots only; `wall` items snap to wall tracks; `ceiling` items go to the center. An empty slot shows a "+" marker.
- **Overlap:** items overlap in an isometric room by nature; they are depth-sorted (`x+y`), a tap picks the top-most pixel (alpha hit test), a selected item is outlined and brought forward, and while dragging the items in front turn translucent.
- **The catalog drawer** (a bottom sheet on phones, a side panel on large screens). Opened from a "+" button for the whole room, or by tapping an empty slot or a surface for that place only. Tabs: **For this spot** and **Everything** (Items, Walls and floor). Each card shows the picture, name, level, and one state: *Owned, in storage* (button Place); *In the room* (badge; button Move or Put away); *Can buy* (price, button Buy); *Not enough tokens* (price and "N more tokens", disabled; tapping explains that merging earns tokens). Nothing is hidden: unbought items are visible so the player sees what to save for.
- **Buying:** tap Buy, a confirmation sheet shows the big picture, the price, the balance before and after, "can't be sold back", Buy / Cancel. After buying, a floor item goes straight into place mode (a ghost at a valid spot that the player drags and drops), a slot item goes into the chosen slot, and "Buy another" is offered for items that can repeat. Upgrades and colors use the same confirm sheet.

### Rendering and art
- One fixed-size isometric stage that scales to the screen. Walls and floor are SVG polygons (colors and generated patterns), items are sprites on a 2:1 diamond grid (`sx=(gx-gy)*TW/2`, `sy=(gx+gy)*TH/2`; the tile size and the room size are constants, so rooms can differ), depth-sorted. Wall and ceiling items are drawn front-on and skewed onto the wall in CSS, so they need no isometric art.
- **The reference room's angle is the right one** (standard 2:1 isometric); the overlaps are normal and are handled as above. The real risk is mixing projections: Matan's first furniture sheet is isometric and usable, the second sheet is front-on and fits only wall items. Every floor item faces front-right and the game mirrors it, so the art must be symmetric-safe.
- **One picture per item and level serves both the catalog and the room** (the drawer scales it). Recolorable parts are painted magenta in the art and cut out and recolored by the game, so one sprite gives every palette color.
- `personal-space/room_template.png` is the geometry (10 x 10 floor, 100 x 50 tiles, example footprints) to attach to every Gemini request; `personal-space/GEMINI_PROMPTS.md` has the prompts. Matan's sheets so far: paintbrushes (the color picker), coins and chest (token icon, balance display, unlock ceremony), furniture (see the prompts file for what they are good for).

### Pricing (draft, to tune with the max-out check)
Target about 200 to 250 tokens for everything. Small items 2 to 3, medium 4 to 6, large 8 to 10 to buy; level 2 costs about the buy price, level 3 about twice it; a color 1 token (premium 2); a pattern 2. Budget split about 35% items, 35% upgrades, 30% colors and patterns. The first 10 tokens should buy 5 visible changes (cheap first upgrades and colors) so the room feels alive at once. Limit each item to 4 to 8 colors, or colors alone would eat the budget (16 colors x 15 items = 240 tokens).

## Question controls (granular choice of what is shown)
Per profile, parent area, applied instantly. Three optional layers, coarse to fine; with nothing set the game behaves exactly as before.
1. **Difficulty switches** (easy / medium / hard) at the top of Settings, unchanged. Quick and simple.
2. **"Fine tuning" (closed by default):** a grid of the 7 sections × 3 levels. ✓ shown, ✕ hidden. A switch above sets a whole column; a cell changes one combination. A section whose every cell is hidden disappears from the child's menu (if she was in it, she moves to the mix). The mix (אתגר הקשת בענן) obeys the same cells.
3. **Hide single types:** a checkbox list per section, independent of level.
**Rules:** bonus questions ignore all of it; the settings can never leave nothing to show (refused with a message); today's rule that a section never goes empty because of difficulty alone is kept, so "easy only" works exactly as before, and only the new cells and hidden types can empty a section. Stored as `mx:{off:["section:level"], hide:[skill]}` next to `diff` in the profile's progress, so backup codes and cloud sync carry it.
**Step 2, focus on weak spots (built).** A per-profile switch in Settings, off by default. Exactly what it does:
- About **4 of every 10 questions** are drawn only from the types currently labelled 🌱 "needs practice" in that profile's Progress tab. The other 6 are drawn as usual, so she never gets only what is hard.
- If no type is 🌱, the 4 in 10 come from the types labelled 🌿 "on the way". If there are none of those either (or no data yet), the game is completely normal.
- A type is labelled only after 8 answers, and only its last 30 answers count, so a type that improves leaves the pool by itself.
- It chooses only among what the section, the difficulty switches and the fine tuning already allow. Hidden types and cells are never drawn, even if weak. The mix draws from all allowed sections; inside one section it stays in that section.
- Bonus questions are not affected. The child sees nothing different.
- When several types qualify, it does not pick the same one twice in a row; with a single weak type it may repeat.
- The settings card shows which types are in the pool right now, so a parent can see what it will do before turning it on.
**Step 3, warm-up first (built).** A per-profile switch in Settings, off by default, independent of focus. Exactly what it does:
- The **first 5 regular questions of each session** are drawn only from the types currently labelled ⭐ "solid", so a session starts with a few wins. A session is each time the game is opened, and each time the profile is switched. After 5, the normal draw returns (and focus on weak spots, if it is on; while warming up, focus does not apply).
- If no type is ⭐ yet (a label needs 8 answers), there is no warm-up and the game is normal.
- Same limits as focus: only what the section, difficulty switches and fine tuning allow (a hidden type is never used); bonus questions are not affected and do not count toward the 5; the child sees nothing different. The same type is not repeated back to back when several qualify.
- The card shows how many types are available for warm-up right now.
Both work inside the matrix and never override it. Skipped on purpose: automatic difficulty changes, per-type difficulty sliders.

## Explanations

### Focus mode (not built) and wrong-answer labels (built)
**What the game already records.** Every answer is logged per profile: the question type, level, correct or not, seconds, date, and for wrong answers the answer chosen and the right one. The Progress tab already labels every question type by how it is going (🌱 needs practice, 🌿 on the way, ⭐ solid, from the last 30 answers of that type, only after 8) and shows the most common wrong answers for a type.

**Focus mode** changes the game, not just the report. When the parent turns it on for a profile, the game draws more questions from the types marked "needs practice": about 40% of questions, never blocking the others (more than that tends to feel punishing). It is off by default. A type leaves the practice pool as soon as its label improves, so a child who gets better sees it naturally fade.

**Wrong-answer labels (built).** Instead of per-generator work, the game classifies each logged mistake from the answer chosen and the right one, so existing history is labelled too. Labels: off by one, off by ten or a hundred, digits in the wrong place (36 for 63), sign flipped, double or half, tens digit wrong, ones digit wrong. The Progress tab shows a skill's common mistake type only with at least 3 wrong numeric answers and a clear pattern (at least 2 and 30% of them); otherwise it says nothing rather than guess. **Limits:** only numeric answers are labelled; "added instead of subtracted" and "picked the first option" need the question's numbers or the option position, which are not logged, so they are not built. Original idea: this names the kind of mistake. Today the game stores the wrong answer ("she chose 50 instead of 40") but not why. A label says, for example: off by ten, place-value slip (tens and ones swapped), picked the first option, added instead of subtracted. The Progress tab could then say "often off by ten in two-digit subtraction" rather than just "needs practice", which is far more useful for a parent helping at the table. It needs a small amount of extra work in each question type, because only the generator knows which wrong choice stands for which mistake. Suggested order: do the most common types first (addition, subtraction with borrowing, place value), then add labels as they prove useful.

### Home screen and offline support (built)
**Status.** Built: manifest, icons, service worker (network first, saved copy as fallback), update notice with "reload", persistent-storage request, iPhone "add to home screen" steps and an install button on Android/desktop, all on the Backup page. It only activates when the game is served over https (or localhost); the file opened locally and the artifact preview skip it silently. Deploy `math-quest.html`, `manifest.webmanifest`, `sw.js` and the four PNG icons together. **Each release must change `APP_VERSION` in the game and `VERSION` in `sw.js` to the same value**; a test checks this. Original explanation follows.
**The problem.** The game is a web page. A parent opens it in a browser, so it needs a connection to load, there is no icon on the child's home screen, the browser bar and tabs are visible, and on iPhones and iPads Safari can erase a site's stored data after about a week without use unless the site was added to the home screen.

**What it would be.** Three small pieces:
1. A *web-app manifest* (a small file with the name, colors and icon). With it, "Add to Home Screen" gives the game its own icon and opens it full screen like an app, with no browser bar.
2. A *service worker* (a small script) that saves the game page in the browser after the first visit, so it opens instantly and works with no internet. The cloud backup keeps working the same way: the game saves locally and syncs when a connection returns.
3. A *persistent-storage request* and a friendly "add to home screen" hint on iPhones. Home-screen apps on iOS keep their data much more reliably.

**Cost and catches.** Roughly half a day. The service worker has to be told to fetch the new version when the game changes, otherwise families keep running an old copy; the usual approach is to check for a new version each time the game opens and offer "reload". It needs the game to be served over https (GitHub Pages is), so it does not apply to the file opened locally. The game is one file with embedded fonts and images, so the offline copy is just that file plus the icon. Not built until you decide.

## Design decisions kept for reference

### How a skill is assessed
- Window: the last 30 answers of that type (not the last 30 overall), so rarely seen types still get a fair read. Fewer than 8 answers shows "not enough data".
- Labels, absolute: under 60% needs practice; 60 to 85% on the way; over 85% solid. Four-choice questions have a 25% guessing floor.
- Speed (median seconds) is shown beside accuracy. The label says how she is now, not how she got there.
- The trend arrow compares the last 30 with the 30 before, only when both have enough data and the change is over about 10 points. It never changes the label.
- The log keeps the 2,000 most recent answers per profile (about 140 KB); older ones are folded into small daily summaries. Trend and "repeat offenders" use the whole log.

### Question difficulty
Each type has a rating in `SKILL_DIFFICULTY` (1 easy, 2 medium, 3 hard). The parent switch is per profile, at least one level stays on, bonus questions are always hard and ignore it, and if a section has nothing at an enabled level the closest level is used. Rule: every section has at least 2 regular types at each difficulty (checked by tests). A bonus must really be hard: three types that were bonus became regular medium types, and old statistics under their old ids are remapped (`SKILL_ALIAS`).

### Saving progress (decision)
Chosen design: **three options on the Backup page** (see Built). A recovery-code-only option was dropped because the anonymous family code replaces it. Guest mode stays the default, with no login wall.

### Cloud: family model
- Progress lives in a *family* (`families/<26-character id>/profiles/<profile id>`). A Google account owns one family (`users/<uid>` stores its id) and every device that signs in with the account joins it. A device that cannot use Google (for example a child's Family Link device) joins with the family code, or starts an anonymous backup from its own progress.
- A family id is 130 bits of randomness; the collection cannot be listed, so ids cannot be discovered. Whoever holds the code can read and change that family's progress.
- Conflicts: per profile, newest copy wins, with a local safety copy before any pull. A mistyped code creates nothing. Repeated sign-in events never create a second family (found by the tests).
- Wiping a family does not stop devices that are still connected from re-uploading; disconnect them first.
- Why not a child's own Google account: it needs the parent's Family Link approval per device, stores a child's identity, and fails on school-managed devices. It can be added later as a third way to join without redesign.
- Free-plan capacity: about 400 to 900 players playing on the same day (writes are the first limit). Details in `firebase/SETUP.md`.
